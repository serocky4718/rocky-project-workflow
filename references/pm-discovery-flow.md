# PM Discovery Flow

先把模糊想法整理成可执行 PRD；PRD 确认前不写业务代码、不安装依赖、不执行 Git 写入或外部账号操作。

创建新项目和手动进入 PM 使用同一份 `roles/pm.md` 职责与完成标志。本文件只补充需求探讨和骨架生成步骤，不另建一套交付规则。

## 探讨顺序

1. 理解项目目标、目标用户和核心问题。
2. 确认 MVP、明确本阶段不做什么。
3. 补齐会影响方向的登录、支付、数据库、AI、上传、后台和部署需求。
4. 按 `project-scale-rules.md` 推荐 XS/S/M/L。
5. 按 `execution-modes.md` 推荐执行模式；默认 `Guided Solo`。
6. 输出 PRD 草案并请求用户确认。

每轮只问少量关键问题，并解释为什么需要回答。

## PRD 草案最低内容

```text
项目名称与一句话目标
目标用户和核心问题
项目规模、执行模式及理由
MVP 范围与本阶段不做
主要用户流程或模块
数据和权限需求
验收标准
风险和待确认项
```

模型建议只在当前界面允许用户选择模型时提供。使用“标准代码模型 / 强推理代码模型 / 最强可用模型”等界面可理解的能力描述，不使用 B0/B1/B2/B3 自造档位。

## PRD 确认后

1. 根据规模列出准备创建的文件和目录。
2. 说明影响、风险和成功标志。
3. 优先运行 `scripts/init_project.py` 的预览模式。
4. 确认预览没有覆盖现有文件后，再使用 `--apply` 写入。
5. 按 `roles/pm.md` 将聊天中已确认的内容写入 PRD；M/L 同时填写当前执行切片，TASKS 写入有负责人、验收与依赖的实际任务。不要把空模板当作已保存需求。
6. 按 `state-and-handoff.md` 记录用户确认的来源，同步 TASKS、HANDOFF 与工作流阶段；运行 `validate_project.py --level ready`。失败时补齐文件或解决冲突，不让用户重复确认已确认的内容。
7. Guided Solo 在已授权范围内进入下一阶段；Strict Handoff 更新交接后交给用户；Dispatcher 由调度者接手。GitHub 授权单独处理。

## GitHub 是单独的可选步骤

项目文件创建完成后，先问：

```text
是否要把这个项目同步到 GitHub？
```

只有用户明确同意后，再问：

```text
仓库要使用 public 还是 private？
```

用户没有同意 GitHub 同步时，不访问账号、不创建仓库、不配置 GitHub remote、不 push。PM 阶段仍不执行 Git 写入；后续 Builder 的本地存档按本地操作规则执行，不需要 GitHub 同步授权。

## 成功标志

```text
PRD 已确认
确认内容已保存到 PRD 和实际任务，确认来源已记录
就绪检查通过，阶段与交接一致
规模和执行模式已写清
只生成该规模需要的文件
AGENTS.md 已生成
下一阶段明确
GitHub 未被默认触发
```
