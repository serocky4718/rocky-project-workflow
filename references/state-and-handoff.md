# State And Handoff

`WORKFLOW.json` 是阶段的唯一状态来源。TASKS 与 HANDOFF 的 `Stage` 是同一状态的展示字段，HANDOFF 第一节用一句话解释该阶段，第三节写真实下一步。确认记录只记录用户已经做出的决定，不创造授权。

## PM 保存确认并交接

1. 生成骨架后，把聊天中用户确认的正文写入 PRD，整理实际任务；M/L 填写 PRD_CURRENT。
2. 确定实际下一阶段。使用同步脚本预览，将确认来源、阶段、上一阶段结论和下一步一起写入。已获授权的普通保存可以直接在预览无误后执行，不另问一遍确认。
3. 进入实现前运行就绪检查。失败则补齐文档或解决冲突；需求未变化时不让用户重复确认 PRD。

```powershell
python "<skill>/scripts/update_workflow.py" "<project>" --stage builder --summary "用户已确认 MVP；需求和实际任务已保存" --next-step "Builder 实现 TASKS 中的 T-002，并运行项目已有验证" --confirm-prd --confirmation-note "用户在本次对话明确确认了这份 PRD"
# 预览无误后，对同一命令添加 --apply。
python "<skill>/scripts/validate_project.py" "<project>" --level ready
```

示例摘要、任务编号和确认来源必须改成实际内容。脚本不编写 PRD，也无法判断用户是否真的确认；记录前必须有真实对话依据。

## 阶段变化

优先用 `update_workflow.py` 同步三份文件；没有脚本时可按上述字段手动更新，随后检查一致性。普通阶段变化不使用 `--confirm-prd`，已有确认会保留。

需求范围确实变化时返回 PM，用 `--reopen-prd` 清除旧确认和旧调度结果，再讨论新范围。不要沿用上一版本的确认启动新需求。

Dispatcher 的真实轮次、工作版本和角色结果由调度者根据实际交付记录；同步工具不编造 Agent 或通过结果。进入 QA 需要当前 Builder 完成，进入 Reviewer 需要当前 QA 通过；代码变化后旧验证结果失效。

Dispatcher 子 Agent 不调用同步工具来提前切换总阶段，也不改写总任务或交接状态。调度者在收到明确交付后更新角色结果，再同步实际下一阶段；避免多个角色同时维护同一份总进度。

## 文件安全与兼容

默认只预览；`--apply` 才写入阶段字段和交接小节，保留任务表、用户说明及未指定的注意事项。检测到并发修改时停止；写入失败时检查是否产生部分更新，先解决一致性问题，不直接覆盖。

已知兼容的 0.3.x 状态可继续使用；旧文件缺少字段时，同步工具补入 Stage。版本号不同本身不要求迁移，实际规则冲突、未知版本或不兼容结构仍需检查。成功标志：就绪检查通过，工作流、任务和交接给出同一个阶段及可执行的下一步。
